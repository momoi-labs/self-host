Implementation plan · September 11, 2026 · Updated after Incus validation

Development environments

Create an Ubuntu system container from the console, install the selected tools with mise, and run T3 and agents as native processes. Keep SSH access available when the Platform is stopped.

1. Console prototype2. Create environments3. Bootstrap4. Maintenance

Starting decisions

  • Use one Ubuntu LTS base image, with the resolved Incus image fingerprint recorded. Install tools after boot. No custom disk-image builder or OS catalog in this iteration.
  • Use Incus system containers. Colima hosts Incus on macOS; Linux can run Incus directly. The Operator accepted the shared Linux kernel boundary. See the feasibility tests and ADR-0022.
  • Reuse development recipe fields and tool selection. An environment is a separate managed resource, with its own lifecycle. It does not become a Compose Application.
  • Keep the existing development images usable. Copy their recipe settings into an environment configuration; do not migrate containers, credentials or volumes automatically.
  • UI term: Development environments. Each environment owns one system container and one saved recipe. The term is recorded in the domain glossary.

The Colima experiment proved DNS, HTTPS and SSH recovery for a Linux test Host. It did not test native T3 provisioning or a instance without Docker. Those remain acceptance checks below.

Stage 1 · Simulated state only

Prototype the console

Build a temporary route inside the existing React console, using its components and styles. Start with the form and lifecycle interactions before connecting a backend.

  • List environments with name, instance state, T3 readiness and current operation. Show an empty state and a clear Create action.
  • Creation form: name, CPU, memory, disk, Ubuntu version shown read-only, public SSH key, tools and versions, verification commands, and T3 service command and port. Use the existing T3 template with guest paths adapted.
  • Detail view: configuration, installed versions, operation progress, logs, Open T3 and copyable SSH/tunnel instructions.
  • Simulate creation, bootstrap failure, retry, running instance with unavailable T3, stop/start, restart, update failure and deletion. Show errors at the failed step.
  • Saving configuration does not apply an update. Show pending changes and require an explicit Apply update action.

Acceptance: walk through creation and all maintenance actions, including failure states, without creating an environment. Review the prototype with the Operator before connecting it to live actions. Run the required console build.

Stage 2 · Real environment, SSH and durable operation state

Create environments

  • Validate a disposable Ubuntu system container through Incus on the Mac and a Linux Host. Check SSH, network access, storage quotas and restart behavior. The Mac feasibility tests passed; native Linux execution remains a coverage gap.
  • Add one runtime module that owns create, inspect, start, stop, restart and delete operations. Keep runner commands inside it. Implement one real runner; do not build a provider registry.
  • Persist a stable environment ID, runner instance name, configuration, observed instance state and last operation in Platform State. Use a dedicated instance prefix and never adopt unrelated instances.
  • Execute as the Host's Operator account. Validate the daemon's access to the runner, files and virtualization tools in its actual service context.
  • Run long operations outside HTTP requests. Save the operation before launching it, allow one mutation per environment, retain progress and detect interrupted work after a Platform restart. Inspect existing resources before retrying creation.
  • Give the guest its own writable disk. Configure SSH with host-key verification and retain private keys outside API responses and logs. Do not mount the Host's home directory by default.
  • Provide a reachable SSH endpoint through the Host. Use SSH tunnels for initial web access. Do not require household DNS changes or a public router port per instance.

Acceptance: Create in the console produces one real instance and working SSH. Repeating a request or restarting the Platform does not create a duplicate. SSH remains usable with the Platform stopped.

Stage 3 · Native tools and a supervised T3 process

Bootstrap the environment

  1. Wait for base OS initialization through Incus exec, then install and enable SSH. Record failures separately from instance creation.
  2. Prepare the development user and directories for repositories, T3 state and credentials in the guest home. Install OS prerequisites such as Git, CA certificates, build tools, Python and process utilities.
  3. Install mise, write the saved tool configuration, install dependencies as the development user, and record resolved versions. Configure the same executable paths for SSH shells, T3 and agent subprocesses.
  4. Run verification commands as the development user, with bounded runtime and visible output. Include the native PTY check used by the T3 recipe.
  5. Install a systemd unit with an explicit user, home, working directory and command. Start T3 and check its HTTP response separately from instance state.
  6. Show the access instructions and remaining agent authentication steps. Credentials stay in the instance. Logs must not expose credentials or pairing tokens; pairing output needs an explicit authenticated action.

Make bootstrap safe to repeat on the same instance. Preserve repositories, credentials and T3 state. Record the last completed step and allow retry after a package or network failure.

Validate browser access through SSH using the chosen hostname and certificate trust. This must work without the Platform proxy, including on the Operator's Teleport connection. A future integrated Hostname shortcut must not replace the independent access path.

Acceptance: T3 and one authenticated agent run as native guest processes. Closing the client preserves an active task. Repeating bootstrap preserves personal state. After a instance reboot, T3 starts and saved conversations remain accessible; active task survival across a reboot is not promised.

For this iteration, Update means tools and service settings. OS upgrades, instance recreation, resource resizing and automatic rollback are separate work. Removing a tool from a recipe stops managing it; do not automatically uninstall dependencies during the first update implementation.

Acceptance: run the full lifecycle against a disposable instance, including an interrupted update and a failed delete retry. Check real state after every action. Restarting the Platform must not lose progress or apply the same destructive action to another instance.

Implement the stages in order. Stage 4 can land as two changes: start/stop/restart/delete first, then update. Add tests for duplicate requests, interrupted operations, data preservation and deletion ownership. Use real instance smoke tests for SSH, boot and native service behavior.

This plan does not change the existing Compose ownership rule in ADR-0021. Supporting instance resources extends the current product scope. Record that decision before merging the live backend.

Deferred: arbitrary OS images, multiple runner implementations, automatic container migration, OS upgrades, snapshots, backups and automatic rollback. No existing environment needs to be migrated to validate this plan.

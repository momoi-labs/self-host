Native applications on macOS

Keep one non-administrator account per Application on macOS, following the existing Linux model. Reuse s6 and add a restricted privileged helper so the Platform can keep running as the Operator.

Selected approach

The installer uses administrator permission once to install the helper, its restricted authorization rule and the native supervisor. Each deploy creates or reuses an Application Account. The Application's command runs as that account, with no administrator or sudo grant.

Linux already implements this account model. The macOS work is a port of account and process setup, plus the privilege boundary needed by its existing non-root Platform service.

Support foreground, headless commands whose children remain in the service's process group. Commands that daemonize or detach into another group are outside this MVP.

Include in the MVP

  • A dedicated account, group and data home for each Application.
  • Create, configure, start, stop, restart and delete through the existing console.
  • Application Variables, private tool directories, mise recipes and redacted logs.
  • HTTP on the LAN through the existing proxy and DNS, plus unpublished workers.
  • Crash restart, API restart and persisted running or stopped intent across reboot.

Leave for later

  • CPU, memory and task limits, resource metrics and the native terminal.
  • Managed PostgreSQL connections for native macOS consumers.
  • Git source builds, GUI apps and detached process trees.

Implementation status

The macOS s6 build now passes startup, crash recovery, foreground child cleanup, persistent stop and scanner shutdown. A targeted skalibs select patch fixes the reproduced internal-pipe failure.

The runtime port, restricted helper, installer, Host capabilities and release packaging are implemented. Privileged account and lifecycle tests are wired into the disposable Apple Silicon CI fixture. Local execution of that fixture is blocked by interactive sudo authorization.

Release gate: run the privileged fixture and the LAN/reboot acceptance steps in the macOS native guide. Compilation and rootless checks do not establish full Host acceptance.

2. Execution rules and technical decisions

Identity and directories

Keep NativeDefinition.account=sf-app-<id>. Use macOS account tools to allocate a unique nonzero UID and private group under a provisioning lock. Mark ownership, make repeated provisioning safe and refuse an existing account the Platform did not create. Disable interactive authentication, use a non-login shell and grant neither administrator membership nor sudo access. Hiding an account alone does not disable login.

Use root-controlled supervision storage under /Library/Application Support/self-host/native/ and separate Application homes under /Library/Application Support/self-host/native-data/<id>/. Preserve private homes, controlled PATH, Variables and working-directory checks. Keep the Operator's existing Platform state where it is.

Before exec, remove inherited group access, set the Application GID and UID permanently and verify the resulting identity. On Darwin, validate saved IDs and group-expansion behavior as part of the port. Fail without launching if any step fails. Do not claim Linux no_new_privs parity; its direct equivalent was not established. Apple identity-changing calls.

A small privileged entry point

Add a fixed native-control subcommand in a protected copy of the existing binary, for example /Library/PrivilegedHelperTools/dev.momoi.self-host. The Operator's daemon calls it with /usr/bin/sudo -n. Bootstrap installs a sudoers rule for that exact path and subcommand, scoped to the Operator. No wildcard commands or administrator grant goes to an Application Account. Sudo command matching.

Send bounded typed requests on stdin and return structured results or the existing log stream. Derive account names and paths from validated Application IDs. The helper rejects arbitrary account names, root commands and caller-selected privileged paths. Keep the binary, its ancestors and supervision definitions protected from both Operator and Application writes. Missing authorization fails clearly instead of prompting during a deploy.

This reuses sudo authorization and the existing binary. It needs no new resident RPC service. The independent root s6 scan tree performs launch setup; every Application command, including mise and setup, runs only after switching to its dedicated account. Verify the sudoers rule with visudo, update helper and client versions together, and remove the rule during uninstall.

Stop and recovery

s6 already starts each service in a separate session. Reuse timeout-kill, flag-timeout-killpg and the process-group argument passed to finish. The macOS runner must keep ordinary children in that group, forward graceful termination and clean remaining group members before a restart. Validate these options against the pinned s6 version. Supervisor behavior and service directory controls.

Do not signal the Platform's group or an unverified stale process-group ID. Test preparation failure, main-process exit and runner crash as separate cases. Preparation must also have supervised cleanup when the API exits. Detached children are not covered by this contract. Do not add UID-wide process killing as an untested substitute for cgroups.

Tools, readiness and unavailable features

Reuse the per-Application mise recipe. Its installer supports macOS, but each requested dependency and setup command must also support it. Mise installation.

Use bounded /usr/sbin/lsof calls inside the privileged native path and machine-readable fields to verify the listener belongs to the Application UID and service group and binds only to loopback. Refuse wildcard listeners, another process's port and inspection errors. Confirm IPv4 and IPv6 cases on the actual Mac. Lsof options.

Reject every nonempty resource limit on macOS. Return no resource sample and show "Unavailable on this Host", rather than zero usage. Hide or disable native terminal and managed database connections, and reject direct API attempts too. Dedicated accounts preserve NativeEndpoint's identity model, but the macOS database workflow still needs its own validation and remains outside this MVP.

Boot without login

Install one independent native scan LaunchDaemon as root, with RunAtLoad and KeepAlive, using the protected binary and s6 bundle. Preserve the existing Platform and Colima daemons under the Operator. Applications start under their own accounts before login. Bootstrap configures the privileges once; subsequent native operations use the restricted helper. Apple's launchd guide.

The wired LAN, disk-unlock and sleep prerequisites in the macOS Host guide still apply.

3. Implementation order and completion criteria
  1. Validate s6, then port one execution path. Reproduce the scanner shutdown failure with the pinned sources and test its macOS event backend. Prefer an upstream fix or a bounded build patch if needed. Then add the restricted helper, macOS account provisioning, launch setup and process-group cleanup. Done when a foreground service runs as its dedicated non-administrator account, cannot read another private home, stops with its children and leaves unrelated processes alive, and the scanner exits cleanly.
  2. Complete the existing native workflow. Wire recipes, Variables, logs, readiness and reconciliation. Supervise setup independently of the API's lifetime. Done when preparation failure leaves no supported child processes, configuration preserves stopped intent and an API restart neither duplicates nor stops the Application.
  3. Make the console match the Host. Add one small backend capability response consumed by the current native form and detail view. Show the Application Account, hide unsupported controls and validate API requests. Follow the console page skill. Record the macOS helper and process-group contract in a new ADR extending ADR-0031 and in the native guide. The existing domain definition of Application Account stays valid. Done when the console offers only the MVP behavior and Linux keeps its current controls.
  4. Validate boot, then prepare the LAN release. Extend install.sh, uninstall.sh, release-s6.sh, release-cargo.sh, GoReleaser and the artifact jobs. Done when a fresh install and upgrade preserve Application data and intent, and the app answers from another LAN device after reboot without login.

First validation target: the existing Apple Silicon Host. Keep current Intel binary builds; claim Intel native support only after its bundle and runtime have been exercised. Build macOS s6 with the macOS toolchain, not the Linux static-musl recipe. Install the bundle in a protected third-party directory such as /Library/Application Support/self-host/s6, never /usr/libexec. Do not execute an Operator-writable Homebrew binary as root. Apple filesystem protections.

Do not publish a release in this assessment. A later release needs evidence from the packaged install, not only a development build.

4. Validation checklist for implementation

Evidence collected during assessment

A temporary unprivileged fixture on macOS 26.6.2, arm64, compiled s6 and skalibs 2.15.1.0 with clang. Service start, stop and the persistent down file worked. Scanner shutdown failed. The event-backend explanation is a hypothesis, not a tested fix. See the research record.

Automated checks

  • Account tests for unique IDs, idempotency, interrupted provisioning, foreign-account refusal, disabled login, no administrator membership, private homes and safe account removal with retained data.
  • Helper tests for unauthorized callers, malformed requests, arbitrary paths, writable binaries, failed identity changes, saved IDs and clean environment. Prove main and setup commands never start as root or the Operator.
  • macOS integration tests for non-root execution, ordinary child cleanup, crash recovery, preparation timeout, unrelated-process survival and stopped intent.
  • Readiness tests for a valid loopback listener, wildcard binding, occupied port, another service group and inspection failure.
  • API tests that reject foreign users and unavailable limits, terminal and database connections without starting work.
  • Run npm ci && npm test && npm run build in console/, then cargo fmt --check, cargo test --no-fail-fast and cargo clippy -- -D warnings. Add macOS runtime tests to CI; today's macOS job only compiles.
  • Run the existing privileged Linux native integration suites on their disposable Linux fixture. A normal cargo test skips those ignored tests.

Manual console test after implementation

Rebuild the console and use the real backend from cargo run -- serve, with a disposable Platform configuration and nonconflicting ports. Confirm the running build and record its actual console URL. Do not run it against the live LAN state. The URL below is a template, not a running test server.

  1. Open https://admin.<dns-suffix>. Click Deploy application, then choose Native process. Expect unavailable resource limits. After deployment, Summary must show a dedicated sf-app-* account.
  2. Name it mac-native-mvp. Add dependency node, version 24, and Variable MVP_MESSAGE=mac-native-ok. Use the command below, enable HTTP and set port 18765.
node -e 'require("node:http").createServer((q,r)=>r.end(process.env.MVP_MESSAGE)).listen(18765,"127.0.0.1")'
  1. Click Deploy. Expect preparation output in Logs, then a running Application. Open its displayed Hostname. Expect mac-native-ok.
  2. Change MVP_MESSAGE in Variables and save. Expect the new response after the operation completes, without repeating tool installation.
  3. Click Stop, then Start, then Restart. Expect the route to disappear while stopped and the response to return afterward. Confirm ordinary children exit and another Application stays running.
  4. Restart the development API. Expect the same Application instance and restored route. Then deploy an unpublished worker. Expect logs and lifecycle controls with no Hostname.
  5. On the packaged LAN Host, leave one Application running and another stopped. Reboot, without logging in. From a second device, expect the first Hostname to answer and the second to stay stopped. Repeat after an upgrade.

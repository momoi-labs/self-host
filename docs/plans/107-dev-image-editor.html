Development image editor

Implementation plan for #107, extended with the decision from the prototype: variant A (sectioned form, log dock) and model 1 (builder generates, "Edit Dockerfile" takes over the file).

1. Goal

An Operator can install anything mise cannot, in two ways:

  1. Setup: a list of shell commands that run as root, with network, after mise install and before the build checks. This is what #107 asks for.
  2. Edit Dockerfile: take the generated file and own it. The Host builds exactly that text. Going back to the builder discards the edits and regenerates.

The form gains sections in Dockerfile order and the build log moves to a dock at the bottom of the panel, so a taller form does not fight a side-by-side split.

2. Decisions

DecisionWhy
A recipe holds dependencies + setup + build_checks or dockerfile. dockerfile: Some(_) is the mode switch.One field, one rule. No parser reads text back into chips.
In manual mode the Host runs docker build on the text as is. It does not inject the user, the entrypoint or the checks."Edited, it's yours." Matches ADR-0021 (one owner per file). The editor carries a fixed warning.
"Back to builder" discards the text after a confirmation.Same reason. A regenerate-and-diff flow can come later if it is missed.
The Dockerfile is rendered by the Host, not the console. A new POST /dev-images/dockerfile returns it for a recipe.Single source of truth. The console never carries a copy of the template.
The mise config moves from COPY mise.toml to a heredoc inside the Dockerfile.A hand-edited Dockerfile must be self-contained: the dependencies are in the text the Operator sees and edits. The support scripts (entrypoint, profile, build-checks.py) stay as COPY from the context in both modes.
The image tag hashes the rendered Dockerfile instead of mise.toml.Setup and manual edits must trigger a rebuild like dependencies do today.
Consequence. Every existing image gets a new tag on its next save (different hash input). The Host rebuilds it once. Applications keep their deployed tag until they are redeployed, as today.

3. Backend (Rust)

3.1 Recipe

pub struct Recipe {
    pub name: String,
    pub template_id: Option<String>,
    pub dependencies: Vec<Dependency>,
    #[serde(default, skip_serializing_if = "Vec::is_empty")]
    pub setup: Vec<String>,                 // new
    pub build_checks: Vec<String>,
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub dockerfile: Option<String>,         // new; Some = manual mode
}

Old records deserialize unchanged: both fields default to empty.

3.2 Validation

ModeRules
Builder (dockerfile: None)Existing rules. setup follows the build-check rule: at most 16 commands, 1 to 4096 bytes each, no control characters. Message: "Use at most 16 setup commands, each a single command of 1 to 4096 bytes."
Manual (dockerfile: Some)Text is 1 to 65536 bytes, no control characters other than newline and tab, contains a FROM instruction. dependencies, setup and build_checks must be empty; the console sends them empty. Name rule as today. Template id is kept for the listing but not validated against anything new.

3.3 Rendering

DOCKERFILE becomes a template with two holes. Recipe::dockerfile_text() fills them; in manual mode it returns the stored text.

# ... base, user, env, mise install (unchanged) ...

# --- dependencies (mise) ---
COPY <<'EOF' /opt/mise/config/config.toml
[tools]
"node" = "24"

[tasks.check]
run = ["node --version"]
EOF
RUN mkdir -p /data/home /tmp/mise-home /opt/mise/cargo \
    && HOME=/tmp/mise-home CARGO_HOME=/opt/mise/cargo mise install --yes \
    ... (unchanged)

# --- setup (root, with network) ---
RUN curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash
RUN chown -R "${USERNAME}:${USERNAME}" /opt/mise

# --- runtime and build checks (unchanged) ---
COPY runtime-profile.sh ...
...
  • Each setup command is its own RUN line so the log points at the failing step. The trailing chown is emitted only when there is at least one command.
  • Without setup commands the section is a single comment line, so the file still reads in order.
  • The heredoc uses a quoted delimiter so $ in versions is not expanded. TOML content is already JSON-escaped by mise_toml(); keep that function, it feeds the heredoc.
  • image_tag() hashes dockerfile_text().
  • write_build_context() writes dockerfile_text() as Dockerfile and no longer writes mise.toml. The three support files are written in both modes.

3.4 API

RouteChange
POST /dev-imagesAccepts the two new fields. Validation above.
POST /dev-images/dockerfile newBody: a Recipe in builder mode. Validates with the builder rules (name may be empty here; the render does not need it). Returns text/plain with the rendered file. No state is touched. The console calls it on "Edit Dockerfile".
GET /dev-imagesUnchanged; records now carry setup and dockerfile when set.

3.5 Tests

  • Unit: setup rules reject 17 commands, an empty command, a control character. Manual mode rejects a file without FROM, a file over 64 KiB, and a request that still carries dependencies.
  • Unit: the rendered file places setup after mise install and before runtime-profile.sh; no setup, no chown; manual text comes back verbatim.
  • Unit: tag changes when setup changes, when the manual text changes, and stays when only name or template_id change (update the existing image_tag_uses_the_md5_of_the_exact_mise_file test to hash the Dockerfile).
  • Integration (tests/file_store_api.rs): update the expected tag in development_image_identity_survives_renaming_rebuilding_and_restart; add a save in manual mode that survives a restart and returns the same dockerfile; add a POST /dev-images/dockerfile call and assert the setup line is in the body.

4. Console (React)

4.1 Layout: variant A

DevImages.tsx keeps its data flow (poll, submit, delete). The rendering of the editor changes:

  • The Split/Splitter goes. The card becomes a two-row grid: a scrolling form and a log dock (closed / half / full). The dock opens to half when a build starts, as in the prototype.
  • The form is an ordered list of four sections in Dockerfile order: Image (template, name), Dependencies (chips, unchanged component), Setup (new ShellEditor, one command per line, hint: runs as root, with network, after dependencies), Build checks (unchanged, hint gains "after setup").
  • After the sections, a dashed box: "Need more than these fields?" with the Edit Dockerfile button.
  • The mise.toml disclosure is removed; the Dockerfile view supersedes it.
  • CSS moves from prototype.css into console.css under .dev-image-* names. The <1024px rules for the old split are replaced by the dock at 60vh.

4.2 Manual mode

  • Edit Dockerfile posts the current fields to /dev-images/dockerfile, puts the response in the editor and sets dockerfile state. Failure shows the usual Failure block and stays in builder mode.
  • The manual view shows: name field, the editor (ShellEditor reused; bash highlighting is close enough for a Dockerfile), a "Edited by hand" badge, and the fixed hint: "The Host builds this file as is. Keep the dev user and the entrypoint, or the container will not start. Build checks only run if you keep their RUN --network=none step."
  • Back to builder asks "Keep editing / Discard edits" inline. Discard clears dockerfile; the fields still hold their last values, so the builder shows what it showed before the takeover.
  • Save sends { dockerfile, dependencies: [], setup: [], build_checks: [] } in manual mode and the fields with dockerfile omitted otherwise.
  • Opening a saved image whose record has dockerfile opens in manual mode.
  • Listing: the Dependencies column shows Custom Dockerfile for manual images.

4.3 Small pieces

  • devImageTemplates.ts: templates gain setup: []. chooseTemplate fills it.
  • A pure helper recipeBody(state) in lib/dependencies.ts (or a new lib/devImageRecipe.ts) returns the POST body for both modes, with one node test in console/tests/.
  • The listing's status badge and the delete rules are untouched.

7. Risks

RiskHandling
Heredoc in COPY needs BuildKit with the Dockerfile 1.4 frontend.The template already uses RUN --mount, which needs BuildKit; Docker 23+ ships the frontend by default. Verified on the workstation (29.x). The macOS Host runs Docker Desktop, which is newer. If a build fails on the Mac with "unknown instruction", fall back to writing mise.toml into the context in builder mode and keep the heredoc only in manual mode.
Existing images rebuild once.Expected; noted in the ADR and the release notes.
A pasted Dockerfile can do anything the build user can.Same trust as setup commands and as Compose files today. The Operator is the only user. Out of scope: secrets, non-root setup (as the issue states).
DevImages.tsx grows past comfort.Move the editor panel into components/DevImageEditor.tsx during step 4 if the file passes ~600 lines; no other refactor.

8. Out of scope

  • Merging hand edits back into the builder, or regenerating with a diff.
  • Build secrets, running setup as dev, a Hermes template.
  • Dockerfile syntax highlighting beyond the bash grammar already loaded.
  • Variants B to E of the prototype.

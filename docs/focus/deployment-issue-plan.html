F0 / Define runtime and publication contracts

Workstream: Integration · Blocked by: None

Problem. Application records assume Docker and one published HTTP target. Independent branches would otherwise change the same persistence and API contracts.

Scope. Add the smallest compatible model for container/native execution and explicit publication. Distinguish no route from a route whose target is unavailable. Preserve Application identity. Agree on route records, certificate lookup, native launch requests and database connection references before implementing adapters.

Acceptance

  • Old state and old API requests retain container behavior and their root route; migration is covered by a fixture.
  • An unpublished Application has no DNS/proxy entry or allocated web port. A pending published Application retains its unavailable response.
  • Publish example payloads and ownership boundaries for W1, W2, N3 and P2. Keep new execution paths disabled until their implementations exist.
  • Record the proposed Git/Dockerfile workflow and standalone PostgreSQL Application decision. Update domain docs through the repository domain workflow.

Primary ownership. src/store.rs, src/file_store.rs, request/response types in src/lib.rs, shared console types

Outside this issue. No universal runtime framework, background-controller rewrite, process execution or console redesign.

W1 / Route hostnames and paths to local targets

Workstream: Web · Blocked by: F0

Problem. The proxy can publish only one target per hostname. An Operator cannot map a root route and a separate path to different local ports.

Scope. Add persisted hostname/path rules with loopback targets, explicit preserve/strip behavior and deterministic precedence. Support container and native targets through the same routing contract.

Acceptance

  • On a synthetic hostname, / reaches one target and /app reaches another. /apple does not match the /app path segment.
  • Longest matching path wins; duplicate conflicting rules fail validation. Removing an Application removes only its own rules.
  • Queries, redirects, assets, streaming and authenticated WebSockets work in representative upstream fixtures. Report when an upstream cannot run under a prefix.
  • Rule changes take effect without restarting unrelated Applications. Reserved management and certificate-challenge routes cannot be overwritten.

Primary ownership. src/routes.rs; route table and request dispatch in src/proxy.rs; routing API adapter

Outside this issue. No arbitrary remote upstreams or automatic rewriting of every upstream HTML response.

W2 / Manage public certificates in the embedded proxy

Workstream: Web · Blocked by: F0

Problem. The local certificate workflow does not issue or renew public certificates for independent hostnames.

Scope. Add ACME HTTP-01 issuance, persisted account/certificate keys, SNI selection, renewal and live certificate replacement. Preserve local-CA mode. Use the challenge-handler contract agreed in F0.

Acceptance

  • Use a local ACME test service and a controlled staging test to issue certificates for multiple synthetic test hosts and aliases.
  • HTTP challenges precede redirects and user path rules. Unknown SNI and missing certificates have a defined safe response.
  • Restart preserves account and certificate state. Renewal replaces the served certificate without restarting Applications.
  • Renewal failures remain visible and retain a still-valid certificate; keys have restricted permissions and never appear in logs.

Primary ownership. src/tls.rs; a certificate manager module; TLS acceptor integration in src/proxy.rs

Outside this issue. No external proxy dependency, wildcard certificates or provider-specific DNS automation.

W3 / Expose public routing and TLS controls safely

Workstream: Web · Blocked by: W1, W2

Problem. The Operator needs one place to manage public routes and certificates without exposing a plaintext management API.

Scope. Add route editing, certificate status/retry and an explicit console hostname using the embedded proxy. Keep backend management and database listeners private. Reuse the existing Operator authentication model.

Acceptance

  • An Operator can add, edit and delete a route and inspect issuance/renewal failures from the console.
  • The public console uses trusted HTTPS. The plaintext API is restricted, and unauthenticated API/terminal requests fail through the final public path.
  • App rules cannot shadow management endpoints. Spoofed forwarded headers do not grant trust; direct-edge operation has defined client address handling.
  • Follow skills/add-page/SKILL.md and verify the real console against cargo run -- serve after rebuilding it.

Primary ownership. src/main.rs listener configuration; route/certificate console components and API adapters

Outside this issue. No multi-Operator roles or trusted-upstream proxy product in this slice.

N1 / Launch native processes under isolated Linux accounts

Workstream: Native · Blocked by: None

Problem. Native execution must never run Application commands as root, and resource limits must cover descendants.

Scope. Provision a dedicated non-login account, owned home/data directories and a delegated cgroup v2 context. Define a launch request that can apply identity, environment and limits before executing a command. This module does not expose an Application API yet.

Acceptance

  • Reject missing, empty, unknown and UID 0 identities. Failed group setup, privilege drop or cgroup assignment prevents execution with no root fallback.
  • Main commands, hooks, build commands and later terminals use the same identity policy. Clear inherited privileged credentials, capabilities and supplementary groups; prevent privilege escalation.
  • CPU, memory and task limits cover forked and detached descendants. Stopping the process tree leaves no Application process behind.
  • Linux integration tests prove separate private directories, denied Platform credential access and no default sudo or container-engine access. Cgroups are documented as resource controls, not a filesystem or network sandbox.

Primary ownership. New native identity and cgroup modules with a narrow privileged provisioning boundary

Outside this issue. No general user-management console, interactive Linux login management or macOS native runtime.

N2 / Supervise native process trees with s6 on Linux

Workstream: Native · Blocked by: N1

Problem. A safe launch primitive still needs process supervision, logs and recovery across daemon or Host restarts.

Scope. Install/detect s6, generate protected service directories and implement start, stop, restart, readiness and log capture. Provide Linux boot supervision and cgroup delegation. The Host service manager may bootstrap/delegate; s6 owns Application processes.

Acceptance

  • Use N1 before any Application command executes, including readiness hooks. Applications cannot modify supervisor wrappers.
  • A synthetic process recovers from failure; stop/restart cleans up descendants and retains Application data.
  • Platform restart reconnects to existing supervision without duplicate processes. Host reboot restores intended running/stopped states.
  • Missing s6, unsupported cgroup delegation and unhealthy startup produce actionable errors. Logs rotate and retain per-Application ownership.

Primary ownership. New s6 runtime module; Linux service assets; targeted install.sh changes

Outside this issue. No per-Application systemd backend or replacement of Docker supervision.

N3 / Integrate native Applications into lifecycle operations Reuse #40

Workstream: Native · Blocked by: F0, N2

Problem. Application creation, status and lifecycle operations still assume a container.

Scope. Refresh existing issue #40 around the embedded proxy and s6 implementation. Connect native definitions to existing task/audit infrastructure, persisted intent, status, logs and loopback publication. Keep the current container path intact.

Acceptance

  • Create a native Application with command, working directory, dedicated account, environment, data path and resource limits.
  • Start, stop, restart, update and remove report coherent task/status results. Interrupted work and daemon restart reconcile safely.
  • A native web target binds privately and can be published; a native worker can remain unpublished. W1 performs the final path-routing integration.
  • Removal revokes runtime access and preserves data unless the Operator explicitly requests deletion. Existing container lifecycle tests still pass.

Primary ownership. src/apps.rs native dispatch; lifecycle API adapter; native persistence adapter

Outside this issue. Do not carry the old issue's external-runtime stage, obsolete proxy assumptions or full controller redesign into this release.

N4 / Operate native Applications from the console

Workstream: Native · Blocked by: N3

Problem. The Operator needs native setup and diagnosis without an administrative shell.

Scope. Expose native configuration, lifecycle actions, logs, resource usage and an authenticated terminal under the Application account. Show the execution identity and the difference between resource limits and access permissions.

Acceptance

  • Create and restart a synthetic native Application in the real console; logs, readiness and resource usage reflect the process tree.
  • Configure each Application's mise dependencies and setup commands with the shared dependency editor. Installation, setup, the main process and terminal use its dedicated account and limits. Keep tools, configuration and caches private to that Application.
  • Apply recipe changes before startup, report installation failures, and preserve stopped intent. Ordinary restarts and Variable edits do not repeat a successfully applied recipe.
  • The terminal and every child use the dedicated non-root account and the same cgroup. No inherited administrative credentials are available.
  • Environment and credential editing keep secrets out of ordinary responses and logs. Display only deliberate connection/secret reveals.
  • Follow skills/add-page/SKILL.md, rebuild the console and verify it against the real backend.

Primary ownership. Native console form/detail components; src/terminal.rs native adapter; src/metrics.rs native collector

Outside this issue. No new Operator-role system or automatic copying of an Operator's home directory and credentials.

D1 / Resolve Compose configuration deterministically

Workstream: Deployment · Blocked by: None

Problem. Saved variables are broadcast to services but do not define Compose interpolation. Supported YAML/storage behavior is also incomplete.

Scope. Normalize extension/merge syntax and define a documented supported Compose subset. Resolve variables from explicit Application inputs, including defaults, required values and literal dollar signs. Preserve supported commands, users, health checks and dependency declarations.

Acceptance

  • Table-driven fixtures cover missing/default/required values, escaping and YAML merges. Ambient daemon variables do not silently change the result.
  • Only services explicitly using a secret receive it. Preserve existing Applications through an explicit compatibility/migration policy rather than silently removing injected values.
  • Unsupported keys or volume options fail with a precise error instead of disappearing. Do not claim full Compose compatibility.
  • Provide a stable normalized definition to D2 and P1. Repository-relative env files and builds are materialized by D2; arbitrary Host file reads are rejected.

Primary ownership. src/compose_app.rs parser and renderer; focused Compose fixtures

Outside this issue. No replicas, orchestration cluster or one-shot-job product unless a separate requirement establishes the need.

D2 / Build immutable releases from Git sources

Workstream: Deployment · Blocked by: F0, D1

Problem. A Host filesystem path does not reproduce repository checkout, build inputs or an Application's release revision.

Scope. Implement the proposed minimal Git workflow: repository/ref, pinned commit, build context, Dockerfile and declared build inputs. Materialize supported Compose build/env_file inputs inside that checkout. Keep the existing registry-image workflow.

Acceptance

  • A selected commit builds an immutable image and records revision/build results. A failed build leaves the running release untouched.
  • Resolve paths inside the checkout and reject escapes. User build steps execute in the controlled build runtime, never an unrestricted root shell on the Host.
  • Private checkout/registry credentials have restricted storage and redacted output. Treat build secrets separately from ordinary build arguments.
  • The console can configure the source and trigger a build. No provider-specific OAuth application or automatic buildpack detection is required.

Primary ownership. New source checkout/build module; narrow Docker build adapter; source console form

Outside this issue. Native package/tool installation remains an explicit non-root command flow owned by N1/N3; this ticket builds container releases.

D3 / Trigger releases and report readiness failures

Workstream: Deployment · Blocked by: D2

Problem. Source updates need an authenticated repeatable trigger and a clear outcome when a candidate release is unhealthy.

Scope. Add a signed webhook or scoped authenticated deploy trigger, branch filtering and per-Application serialization. Reuse deployment tasks and retain the previous immutable image/revision for explicit recovery.

Acceptance

  • Invalid authentication and irrelevant branches do not build. Duplicate deliveries do not start duplicate releases; concurrent deploys serialize.
  • The UI distinguishes running from ready and reports failed health checks within a defined timeout.
  • A failed candidate does not report successful deployment. The Operator can redeploy the previous immutable release, with downtime behavior documented.
  • Integration tests cover API-triggered image deployment as well as Git triggers, without leaking trigger credentials.

Primary ownership. Source trigger module; deployment task integration; readiness/status console updates

Outside this issue. No promised zero-downtime rollout or automatic database rollback. A release gate must explicitly accept the initial availability policy.

P1 / Preserve storage and private connectivity for stateful apps

Workstream: Data · Blocked by: F0, D1

Problem. Generated volume names can start an Application on empty storage, and shared networking does not provide private database access.

Scope. Add explicit named-volume mapping or a verified copy path, safe bind-mount handling and consumer-scoped database connectivity. Enable container Applications without an HTTP Web Target through F0.

Acceptance

  • A synthetic existing volume is mapped deliberately or copied with a manifest/check. Restart, redeploy and ordinary removal preserve its data.
  • File mounts remain files and directory mounts remain directories. Supported long syntax and read-only settings retain their meaning; unsupported options fail.
  • Standalone stateful services have lifecycle/health reporting without a hostname, web-port allocation or proxy route.
  • Only declared consumers receive database network access/credentials. Container connectivity and loopback-only access for native consumers have explicit tests; there is no public database listener.

Primary ownership. src/compose_app.rs volume/network rendering; src/docker.rs project materialization; storage adapter

Outside this issue. No automatic adoption of arbitrary live workloads or silent migration of all existing network policies.

P2 / Provision local PostgreSQL through the console

Workstream: Data · Blocked by: P1

Problem. The Operator currently has to author database Compose definitions and wire persistence and credentials manually.

Scope. Use a managed container Application with no HTTP publication. Offer a pinned PostgreSQL major version, database/user creation, generated credentials, durable storage, readiness and explicit consumer connections. This is the proposed first implementation of local PostgreSQL.

Acceptance

  • Create a database in the real console, connect a declared consumer and preserve a test row across restart/redeploy.
  • Show readiness and actionable startup failures. Connection details use private paths and are revealed only through authenticated controls.
  • Accept a compatible logical import with clear job status and validate the imported data. Do not upgrade the major version as part of data migration.
  • Disconnecting a consumer revokes its Platform-managed connection. Removing the database requires an explicit separate choice before deleting data.

Primary ownership. New PostgreSQL provisioning/template module; database console form; connection API adapter

Outside this issue. No high availability, replication manager or additional database engines.

R1 / Export and restore Platform and Application data

Workstream: Recovery · Blocked by: W2, N3, D2, P2

Problem. A Platform configuration copy does not restore databases, file volumes, native home data or queued work.

Scope. Provide explicit backup/restore operations and a runbook covering consistent Platform State, TLS/source credentials, PostgreSQL logical backups, file volumes and native data. Record required stops or queue drains. Produce an artifact the Operator can store off-host.

Acceptance

  • Restore into an isolated empty installation and verify records, credentials, certificate state, database rows and representative Application files.
  • The restore path checks compatibility, ownership and permissions and never attaches the same live database directory to two writers.
  • Backups and logs protect secrets. Failures and incomplete backups are visible; a completed export includes a manifest and verification result.
  • State the manual backup schedule and retention responsibility. Automated scheduling/remote storage integrations remain separately tracked unless made a release requirement.

Primary ownership. Backup/restore module or commands; docs/operating.md; isolated recovery fixtures

Outside this issue. No automatic production restore, cloud-storage provider integration or zero-data-loss claim.

V1 / Rehearse recovery and validate a migration-ready release

Workstream: Release · Blocked by: W3, N4, D3, P2, R1

Problem. Merged capabilities do not prove that a complete deployment can survive restart, failed release and data restore.

Scope. Validate one released build on disposable Linux infrastructure using synthetic web, worker, database and native workloads. Keep any actual migration inventory and access details outside the repository.

Acceptance

  • Verify public certificate issuance/renewal, route precedence, authentication, assets and WebSockets through the final embedded proxy.
  • Verify source triggers, container updates, database import, persisted worker data and native non-root identity/child limits.
  • Reboot the Host, recover interrupted work, restore a backup and exercise a failed deployment followed by explicit release recovery.
  • Record the exact tested release and accepted downtime/backup limits in the private operational record. Public evidence contains only synthetic examples.
  • After the release passes, prepare a separate private cutover plan with backup, traffic switch and rollback checkpoints. Do not perform cutover as part of this implementation issue.

Primary ownership. Synthetic end-to-end fixtures; release checklist; sanitized operating documentation

Outside this issue. A passing unit suite alone does not close this issue; production migration remains a later operation.

Context
Scope decisions

The requirements come from the sanitized readiness assessment and the Operator's choices in this conversation. This plan proposes implementation boundaries; it does not report shipped capabilities.

  • The embedded proxy owns public HTTPS and hostname/path routing.
  • One console Operator is enough. Per-Application Linux accounts are execution identities.
  • s6 owns native process supervision. Every Application command and terminal runs under a dedicated non-root account.
  • The first local PostgreSQL flow uses a standalone container Application with no HTTP route. This is a proposed implementation choice to settle in F0.
  • The proposed source workflow is Git plus declared Dockerfile/Compose build inputs. An external image-publishing replacement remains possible, but choosing it requires rewriting D2/D3 before marking them ready.
  • Manual backup export and explicit deployment recovery are the first proposed recovery baseline. V1 requires an explicit decision about acceptable downtime and scheduling before migration.
How to run the work in parallel

Use one worktree and branch per active issue. Keep one owner per workstream. F0's owner coordinates shared state/API wiring and final integration.

  1. Start F0, N1 and D1 together. N1 and D1 stay behind their module boundaries and add no public native API.
  2. Merge F0 before adapters change shared state. Rebase each branch onto it. W1 and W2 are independent implementations, but Web's owner serializes their edits to src/proxy.rs.
  3. After D1 merges, Data owns the volume/network renderer changes in P1. Deployment owns checkout/build work in D2. Coordinate the small Docker adapter patches.
  4. Build runtime-specific forms in separate components. Serialize registration changes in AppForm, shared console API types and navigation. Each new/reviewed screen follows skills/add-page/SKILL.md.
  5. Only the integrator lands changes to shared persistence, request/response types and common lifecycle dispatch during the same merge window. Feature owners supply narrow patches. This is merge coordination, not a new abstraction layer.
  6. Merge complete dependent slices. Do not enable native execution before N1/N2 enforce identity and cgroups. Begin recovery fixtures early, then close R1 after all persisted-state producers are integrated.

Four workstreams are a maximum, not a requirement for four simultaneous agents. With three execution slots, finish F0/N1/D1 first, then alternate Deployment and Data as blockers clear.

The Operator approved this plan on 2026-09-30. Run up to three implementation tasks per wave, plus one coordinator. Each task uses its own worktree. These waves sequence the existing scope; they add no delivery issues.

Coverage and release limits
  • W1/W2/W3 cover routing, trusted HTTPS, public console access and restricted management listeners.
  • N1/N2/N3/N4 cover accounts, cgroups, supervision, boot recovery, lifecycle, logs, metrics and terminals.
  • D1/D2/D3 cover supported Compose input, variable handling, builds, deploy triggers, readiness and explicit previous-release recovery.
  • P1/P2 cover persistence, private connections, local database creation and data import. R1 covers independent state/data restoration.
  • V1 combines these capabilities and validates existing container lifecycle, streaming and authentication against the selected release.
  • Additional console roles, macOS native execution, scaling, arbitrary workload adoption, one-shot job support, durable monitoring/alerts, DNS-provider automation and zero-downtime releases are outside this proposed first release.
  • Direct public IPv6 support is a separate existing issue (#82). Verify the chosen public DNS/listener path privately before cutover; do not leave unsupported address records active.
  • Do not import unrelated issues into this epic. No live deployment identities, inventories, values, measurements, credentials or access instructions belong in its tickets or PRs.
